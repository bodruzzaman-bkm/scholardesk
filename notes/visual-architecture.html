02 — Lifecycle

What happens when a request arrives

Nine stages, and four places a request can die before reaching the database. The three gates ask different questions, and confusing them is the usual way an authorization bug gets in.

03 — Access

Who can see what

Almost every security question in this codebase reduces to picking one of two query boundaries. They look similar and are not interchangeable.

What each role may actually do

PaperPolicy splits read from write exactly along the collaboration seam.

Action on a paperOwnerCollaboratorAdminWhy
view✅✅✅listing and detail page
read✅✅—open the PDF in the reader
useAi✅✅—AI follows read access
comment✅✅—a comment is addressed to the other people who can see it
annotate✅❌—highlights and notes are one person's private working material
update✅❌—metadata belongs to the owner
delete✅❌——
An administrator is not a super-user here. CollectionPolicy never consults isAdmin() — an admin cannot silently open your private collection. The only place the two role systems meet is comment moderation.

Global role · users.role

researcher — the default.
administrator — promoted by an existing admin. Gated by the admin middleware.

Collection role · collection_members.role

viewer — read papers, notes, comments, feed.
editor — + add/remove papers, comment, run AI.
owner — + manage members, rename, delete.

They are independent

Being an administrator grants nothing inside someone else's collection. Being a collection owner grants nothing in the admin portal.

Suspension, not deletion. Deleting a user cascades through their papers, collections, notes, highlights and comments — destroying a library to silence an account, irreversibly. A suspended user keeps everything and simply cannot sign in, and EnsureUserIsNotSuspended runs on every request so it takes hold immediately rather than when the session expires.
