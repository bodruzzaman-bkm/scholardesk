Part two

The RAG and AI layer, taken apart

Six classes, two pipelines, one rule. The rule is that none of this is allowed to be load-bearing — pull the API key and the rest of the application is unaffected.

The six classes and what each one owns

ClassOwnsThe one thing to know
ChunkServicesplitting text4000 chars per chunk, 400 overlap, breaking at a sentence boundary. The overlap guarantees a passage spanning a boundary is fully present in at least one chunk.
EmbeddingServicetext → vectorWord tokens + character trigrams hashed into 256 dims, log-TF weighted, L2-normalised. No API, no model download, no native extension — it works offline.
IndexingServicethe write pathExtract → chunk → embed → store, in one transaction. Every failure is recorded on the paper, never thrown.
VectorSearchServicethe read pathResolves the access boundary to a concrete id list before scoring anything. Cosine in PHP: exact, not approximate.
RagServiceretrieve → assemble → generate → citeBuilds the context under a character budget derived from the provider's token allowance, then keeps only the citations the model actually used.
AiServicethe provider callEvery provider call in the app funnels through generate(). That is what makes the provider swappable and the whole layer fakeable in tests.

Why the embeddings are lexical, and what that costs

EmbeddingService is the "hashing trick": each word token and each character trigram is hashed to a bucket in a 256-dimensional vector, weighted by log term frequency, then the vector is L2-normalised so cosine similarity is just a dot product.

  • What it buys: semantic search and related-papers work with no API key, no model download, no native extension. The project demos on any machine.
  • What it costs: it matches wording and morphology, not meaning. "neural machine translation" finds "neural translation models"; it will not match a paraphrase sharing no words.
  • The consequence in the UI: because trigrams are shared by any two pieces of English prose, an unrelated query never scores zero — it lands around 0.26–0.29. That is why the display floor exists, and why 0.15–0.32 is a "weak match" band rather than a cut.
  • The seam: swap this one class for a real embedding provider and nothing else changes — the storage format is a JSON array of floats either way.

The prompt budget — the part most projects get wrong

Providers meter tokens per minute, and the reserved completion budget counts against it. Sending a whole paper and hoping produces a rejected request on a free tier. So the budget is computed, not constant:

promptCharBudget()                        AiService.php:58
  tokenBudget   = config(...token_budget)          // 8000 on Groq free
  completion    = config(...max_output_tokens)     // 2048 reserved
  promptTokens  = max(500, (8000 - 2048) * 0.85)   // 15% headroom
  return promptTokens * 4                          // ~4 chars per token

contextBudget()                           RagService.php:37
  return max(2000, promptCharBudget() * 0.75)      // 25% left for
                                                   // question + scaffolding

RagService::answer() then adds retrieved chunks one at a time and stops when the budget is spent — a smaller free tier shrinks the context rather than producing an error.

Why the citation filter is a regex

The prompt asks the model to cite as [P12]. Models reliably drift: gpt-oss emits fullwidth 【P12】, others use parentheses or bold the marker. Matching the literal string missed real citations and silently fell back to listing every retrieved source — which makes citations decorative.

private function answerCites(string $answer, int $paperId): bool
{
    return preg_match('/\bP'.$paperId.'\b/i', $answer) === 1;
}
//  \b … \b  matters: without it, P1 matches inside P12.
